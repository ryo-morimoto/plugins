# レビューコメントを書く規則

PR のレビューコメントの下書きを作るときの基準です。`draft-review-comments` skill と `evaluator` agent が参照します。

この文書は作者個人の基準で、チームの合意ではありません（末尾の「この文書の位置づけ」を参照）。

## 目的

レビューコメントは、相手に判断してもらうための文章です。読む人が、何を見て、何が気になっていて、次に何をしてほしいのかを、短い時間で正しく受け取れることを目指します。

## 優先度の分け方

- 重要な論点は少数に絞り、その論点を議論の中心にします。今後も繰り返し起きて、広がっていく恐れがあるものが、これにあたります。
- そのほかの小さな懸念は、共有にとどめます（決めたいことが無ければ、コメントにしません。「コメントにする条件」を参照）。ただし「問題かもしれない」と書くだけでなく、**なぜ問題になりうるのか**を、原因から結果への流れで添えます。
- 重要度は、長い目で見た費用で考えます。価値の薄いコードが使われて増えること、保守の費用がレビューの余力を圧迫すること、不具合に気づかれないまま利用者に届くことが、その例です。
- 重要度を実際より大きく見せません。挙動が変わらない変更は、優先度が低いものです。
- 重要度の見立ては「低め」「中くらい」「高め」の平易な言葉で書き、暫定であることを添えます。記号や点数は使いません。見立ての内訳（影響、起きやすさ、気づきにくさ）は、読みたい人だけが開ける折りたたみの中に置きます。
- 見立てが「低め」のものは、すぐの対応を求めません。次に取りたいアクションは「認識共有のみ」にします（決めたいことが無ければ、コメントにしません）。「対応をお願いしたい」は、見立てが「中くらい」以上のものに限ります。
- コメントの長さは、見立てに比例させます。低いものを長く書くと、読む人の時間を使わせます。
- 起きやすさは、勘ではなく、リポジトリの履歴（検索の件数、過去のコメント）から出します。断定したくなったら、その場で調べ込まず、アクションを「分析をお願いしたい」にします。
- 合意済みの基準や、決めた範囲に照らして、不要な質問を出しません。出す前に、合意済みの内容を確かめます。
- 読めば意味が分かる具体的な表現に対して、厳しすぎる指摘は出しません。
- 相手に、集めるのが大変な情報を求めません。

## コメントにする条件

- コメントにするのは、読む人に決めてほしいこと（またはしてほしいこと）を、1 つ書ける指摘だけです。共有や相談だけで、決めたいことが無いなら、コメントにしません。
- 「決めたいこと」と「扱う場所」を、③に書きます。扱う場所は、「この PR で直す」か、「別の issue で扱う」かです。
- 別の issue で扱うときは、何を調べ、何を決めたら終わるのか（完了の条件）を添えます。条件が書けないうちは、issue にもコメントにもしません。
- 別の issue にするかどうかは、事業への影響で決めます。影響が小さく、まとめて直したほうが効率のよいものは、個別には issue にせず、負債として積んでおき、全体最適のときにまとめて扱います（チームの方針に合わせます）。その場合の「決めたいこと」は、「この PR で直すか、負債として積むか」です。

## 平易な言葉

- 独自の言葉や、説明のない造語を使いません。短く縮めた言葉は、何を指すのかを、説明する普通の言葉で書き直します。
- 使う言葉は、初めて出たところで定義します。
- 記号や略号は、チームで共有された語彙ではありません。使わず、普通の日本語で書きます。
- 決まりごとへの懸念の理由は、決めつけません。何が気になっているのかを、書く前に利用者に確かめます。

## 辿れる参照

- 調べたこと、文書、コードに基づく主張には、読む人がたどれる参照を付けます。論文や記事の URL、リポジトリのコードへの固定リンク、数を再現できるコマンドのどれかです。「研究があります」とだけ書いて、リンクを付けないことはしません。
- リポジトリのコードへのリンクは、`blob/<40 桁の commit SHA>/<パス>#L<開始行>-L<終了行>` の形にします。ブランチ名や短い SHA は、あとで指す内容が変わるため使いません。PR の先頭（head）か、基準（base）の commit に固定します。
- 自分の推論には出典がないので、「推論」と明記します。出典があるかのように書きません。
- 確認できていないことは、確認できていないと書きます。たとえば、二次的な要約でしか見ていない数字は、載せません。外部の文書は、全文を読めたのか、要約や抜粋だけなのかを区別します。
- 固定リンクが指す行の存在と本文は、スクリプトで確かめられます。ただし、その行が主張に関係しているかどうかは、スクリプトでは確かめられません。人が読んで判断します。

## 口調の基準

レビューコメントは、人が読みます。やわらかく、敬意をもって、過剰にならないように書きます。

- コードについて書きます。人について書きません。相手が何をしたのかを決めつけません。「〜したのなら」のように、相手の行動を前提にした前置きは、推測なので避けます。
- 見たこと、知りたいことを書きます。過去への不満は書きません。「〜してほしかった」のような過去への言い方は、責めているように読めます。
- 命令ではなく、依頼や質問にします。「〜いただけると助かります」「教えてください」の形です。
- 具体的に書き、理由を添えます。
- クッション言葉は、1 回程度にします。「私の理解が違っていたら教えてください」のような一言を 1 回入れ、謝罪や遠慮を繰り返しません。へりくだりすぎた文も、読む人に負担になります。
- 大げさな言葉や、相手を軽く見る言葉を避けます。たとえば、強い断定の言葉、相手の仕事を「ただの〜」と軽く見る言い方、読み手の能力を疑う言い方です。
- 必要がなければ、人名をコメントに書きません。誰が書いたのかを、前提にしません。
- 冒頭に、一般的なレビューのラベル（[Conventional Comments](https://conventionalcomments.org/)）を付けます。新しく入った人が、見慣れた形で読めるようにするためです。`question`（不確かな懸念を尋ねる）、`suggestion`（改善の提案。何を提案し、なぜ役に立つのかを書く）、`thought`（検討中の考え。大きな取り組みの種にもなる）、`note`（知っておいてほしいこと。常にブロックしない）、`issue`（具体的な問題）、`nitpick`（些細な好み）、`todo`（小さいが必要な変更）などです。ラベルのあとに、`(blocking)` か `(non-blocking)` を付けます。例: `suggestion (non-blocking):`。ラベルの付け方は、次の「3 部形式」に従います。

### 出典

口調の基準は、次の文書を参考にして、作者が整理したものです。

- Google eng-practices「How to write code review comments」: https://google.github.io/eng-practices/review/reviewer/comments.html
- CSCW 2022 の研究（破壊的なコメントは、具体性がなく、相手への配慮がないという特徴を持つ、という内容）: https://dl.acm.org/doi/abs/10.1145/3555183（要旨の範囲で確認）
- Conventional Comments（コメントの冒頭にラベルを付ける書き方）: https://conventionalcomments.org/

これらのうち、全文を読んで確かめたものはありません。Google の文書と研究論文は、要約や抜粋で確認した範囲です。観察、理由、依頼の順に書くという考え方も、この基準の背景にあります（出典は未確認）。

## 3 部形式

見立てが「中くらい」以上で、正しそうだと考える指摘は、次の 3 部で 1 つのコメントにします。**1 つのコメントには、1 つの論点だけを書きます。** 論点が増えるときは、コメントを分けます。

### ① 対象の共有（1 行）

何についての話かを、1 行で書きます。対象の場所へのリンクを付けます。証拠のリンクは、②に置き、ここは最小限にします。

### ② 議論や整理をしない場合の課題の可能性

議論や整理をしないまま放置した場合に起きうる課題を、**可能性**として書きます。

- 課題だと断定しません。断定には、対象ごとの詳しい分析が必要で、限られた時間ではできません。「可能性」と書き、断定できていないこと、断定するには何の分析が要るのかを添えます。
- 確認した事実と、推論を分けて書きます。推論には「推論」と明記します。
- 放置した場合の流れを、きっかけ、起きること、誰がいつ気づくか、の順で書きます。
- 根拠の長い説明は、折りたたみ（`<details>`）に入れます。

### ③ 次に取りたいアクション

次の 4 つから 1 つを選び、**何を決めたいのか**と、**どこで扱うのか**（この PR か、別の issue か）を書きます。

| アクション | 意味 |
| --- | --- |
| 認識共有のみ | 共有するだけで、返事も対応も求めない |
| 意見を聞きたい | 相手の意見も聞いて、重要度を判断したい |
| 分析をお願いしたい | 課題かどうかを、分析して確かめてほしい |
| 対応をお願いしたい | 変更や対応をしてほしい |

アクションと、使うラベルの目安です。

| アクション | ラベルの目安 |
| --- | --- |
| 認識共有のみ | `note`。決めたいことが無いので、ふつうはコメントにしない。読む人が知っておくべきときだけ |
| 意見を聞きたい | `question` |
| 分析をお願いしたい | `suggestion`（別の issue で分析する提案など）、`question` |
| 対応をお願いしたい | `suggestion`（変更の提案）、`issue`、`todo` |

- ブロックするかどうか（マージを止めるか）は、ラベルの `(blocking)` と `(non-blocking)` で示し、③にも書きます。
- 対応は必要だが、扱う場所を相談したいときは、「認識共有」に「進め方の相談」を添えます。

## 完成したコメントの例

架空の例です。

```
question (non-blocking): 税額を含めた合計の端数処理について

**対象**: [`total` 関数の金額の計算](https://github.com/example-org/example-repo/blob/<40 桁の SHA>/src/cart/total.ts#L5-L6)

**課題の可能性**: 揃えないまま進めると、金額の端数が計算の場所ごとに食い違う可能性があります。断定はできておらず、確かめるには、ほかの金額計算の端数の扱いを調べる必要があります。

- 確認した事実: 6 行目は、計算結果を丸めずに返しています。
- 推論: ほかの計算が丸めているなら、同じ金額が 1 円ずれて見える流れが考えられます。

<details>
<summary>放置した場合の流れ</summary>

- きっかけ: 別の箇所で丸めた金額と、この関数の戻り値を足したり比べたりする。
- 起きること: 小数を含んだ金額が混ざり、合計や比較が 1 円単位でずれる。
- 気づく人とタイミング: 請求額の不一致に気づいたとき、または集計の突き合わせのとき（推論）。

</details>

**次に取りたいアクション**: 意見を聞きたいです（この PR の中で）。決めたいのは、この関数だけ丸めずに返している理由があるのか、方針が別にあるのかです。教えていただけると助かります。マージを止める話ではありません。
```

## 原文を優先する

- 記録に残す人の言葉（意図、前提、直した理由、却下の理由）は、言い換えずに、原文のまま書きます。人が言葉にしていないことは、書かずに、聞きます。
