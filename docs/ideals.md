# 理想と原則

このリポジトリと、plugin `pr-review` が目指す姿と、そのための原則です。決まったこと、まだ決まっていないこと、やらないことを、分けて書きます。

> 検証中です。内容は変わります。

## このリポジトリの理想

作者の仕事の仕方を、**型**（手順、基準、書式）として常に同期し、**複数の version を試せる**場所にすること。

- 型は、普通のテキスト（Markdown、JSON、スクリプト）で書き、特定のツールに依存しない形に寄せます（[Agent Plugins](https://agent-plugins.org/)）。
- **まだ設計していません。** 「version」を何で区別し（ディレクトリ、タグ、ブランチ）、どう並べて試し、どう比べるかは、決まっていません。

## pr-review の理想

### 目的

PR のレビューで、チームのメンタルモデル（システムの作りと、暗黙のルールの共通理解）を育てることが、主な目的です。リスクの検知は副で、重要度は、チームの成長度合いで変わります（立ち上げの時期は高い）。

### 決めていること

| 観点 | 理想 | 今の状態 |
| --- | --- | --- |
| 人とエージェントの分担 | 人が読んで判断する。エージェントは、下準備・下書き・確認を担う。外部へ出す行為（投稿）は、承認後に人が行う | skill が、承認できる状態までを扱う。投稿の手順は、まだ無い |
| 部品の粒度 | 1 つにまとめず、再利用しやすい複数の部品に分ける。部品ごとに、別の種類の作業や別の人が、変更なしに使えるかを見る | 部品は分かれているが、2 つ目の使い手は、まだ現れていない |
| ツールへの依存 | 最終的には、Agent Plugins の形で、特定のツールに依存しない。移植できる核（普通のテキスト）と、ツール別の薄い包みに分ける | 方向であって、今の事実ではない。動作を確認しているのは、Claude Code だけ |
| 共有の置き場所 | リポジトリとは別の、全員が書き込める場所（マージの流れを通さない）。規則や合意は、データの外に置く | 今はローカル |
| 記録の設計 | 1 件 1 ファイル。一次の記録は書き換えず、要約は作り直せるキャッシュとして扱う | 段階 1 の書式がある。抽象の層は、作っていない |
| コメントの書き方 | やさしく、敬意をもって、平易な言葉で。3 部形式（対象の共有、課題の可能性、次のアクション）。根拠には、辿れる参照を付ける | `rules.md`（作者個人の基準で、チームの合意ではない） |
| 品質の担保 | 独立した確認と、実データでの検証 | `evaluator`、`resolve-permalinks`、`validate-records` |

## review の理想（今はやらない）

共通の観点や型を、成果物の対象（PR、設計書、課題など）に縛られずに、再利用しやすくすること。

**今は、どうすればよいか見通しがないので、取り組みません。** 2 つ目の成果物が現れ、共通の部分が見えてから、改めて考えます。

## 原則

1. **読んで判断するのは人。** エージェントは、下準備・下書き・確認を担い、外部へ出す行為は、承認後に人が行う。
2. **一次の記録は書き換えない。** 要約や言い換えは、作り直せるキャッシュとして持ち、判断の根拠にしない。全面的な書き直しをせず、差分として追記する考え方を借りる。
3. **「なぜ」は、意図・前提・規則に分け、判断した時点で、判断した人の言葉のまま記録する。**
4. **移植できる核と、ツール別の薄い包みに分ける。**
5. **2 つ目の使い手が現れたら、名前を付けて独立させる。** 現れなければ、まとめる。
6. **ツールをまたいで読まれる名前（skill など）は、対象の名前を含める。**
7. **根拠には、辿れる参照を付ける。** 推論は「推論」と書き、確認できていないことは、確認できていないと書く。
8. **新しい基準（命名、書式）は、使う前に共有する。**
9. **計画を厚くしない。** 実際に使って、同じ失敗が 2 回出てから、規則を足す。

## 取り下げたこと

- 「意図の記録は、主張の記録より忠実だ」という比較は、直接は検証できなかった。支持されたのは、「判断した時点で、判断した人の言葉のまま記録する」ことだけ。
- 差分で育てる仕組み（ACE のような、生成・振り返り・整理を回す仕組み）そのものは、採用していない。考え方だけを借りている。
